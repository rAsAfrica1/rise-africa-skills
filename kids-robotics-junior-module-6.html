1. Open-Loop vs Closed-Loop Control

Open-loop control means your robot does exactly what you tell it, with no checking. For example, you program a robot to drive forward for 3 seconds at 50% motor power. If the battery is full, it might go 2 meters. If the battery is low, it might go only 1.5 meters. If one motor is weaker, it veers left. Open-loop is simple and cheapâgreat for fixed tasks like a conveyor belt in a Nairobi packaging plant that moves a box exactly 30 cm every time. But for anything that needs accuracy, open-loop fails.

Closed-loop control uses sensors to measure what actually happens and corrects in real time. A wheel encoder counts rotations. A distance sensor measures how far you really moved. The robot compares the desired position to the actual position, calculates the error, and adjusts motor power. For example, a line-following robot in a Lagos warehouse uses infrared sensors to stay on a painted line. If it drifts right, the left motor speeds up and the right slows down. That feedback loop runs 50 times per second.

In practice, start with open-loop for simple jobs: a robot arm that picks a tomato from a fixed bin. Then add closed-loop when you need repeatability. Use a PID controller (next lesson) for smooth correction. Real numbers: a typical DC gear motor with encoder gives 20 pulses per revolution. At 100 RPM, that's 2000 pulses per secondâenough for precise speed control. Without encoders, your robot will drift 10-20 cm over 5 meters.

For African makers, closed-loop is affordable: an Arduino Uno (about $5) plus two wheel encoders ($2 each) and an L298N motor driver ($3) gives you a closed-loop mobile robot for under $20. Power it with a 12V rechargeable battery. Test on a flat concrete floor. Start by making the robot go straight for 2 meters. Measure the error. Then tune your controller. Closed-loop is how you turn a toy into a tool.

2. PID Control Tuning Methods

PID stands for Proportional, Integral, Derivative. It's the most common closed-loop controller. You measure an error (e.g., difference between desired speed and actual speed). P responds to current error: if error is large, push hard. I responds to accumulated past error: if error persists, push harder. D responds to rate of change: if error is shrinking fast, ease off to avoid overshoot. The magic is in the three tuning constants: Kp, Ki, Kd.

Manual tuning works for most African robotics projects. Start with Ki=0, Kd=0. Set Kp to a small value, like 0.5 for a motor speed controller. Run the robot. If it responds too slowly, increase Kp. If it oscillates (shakes back and forth), decrease Kp. Once you get a quick response with slight overshoot, add Kd to dampen. Increase Kd until oscillation stops. Finally, add a tiny Ki (like 0.01) to eliminate steady-state errorâthe small offset that remains when the robot is close but not exact. For a line follower, typical values: Kp=20, Ki=0.5, Kd=5. For a temperature-controlled soldering iron, Kp=2, Ki=0.1, Kd=0.5.

Ziegler-Nichols is a systematic method. Set Ki=0, Kd=0. Increase Kp until the system oscillates steadily. Note that Kp as Ku (ultimate gain) and the oscillation period as Tu. Then set: Kp=0.6*Ku, Ki=2*Kp/Tu, Kd=Kp*Tu/8. This works well for slow systems like a water tank heater. For fast robots, manual tuning is faster.

Tools: Use a serial plotter (Arduino IDE) or Python with matplotlib to see error over time. Log data to an SD card. In Africa, where power can be unstable, test with a battery, not a wall adapter. Tune on the actual surfaceâcarpet, tile, or dirt. A PID tuned on smooth concrete will fail on gravel. Always test with the robot carrying its real payload. Start with P-only, then add D, then I. Never tune all three at once. Write down your valuesâyou will forget.

3. State Machines and Behavior Trees

A state machine is a way to organize robot behavior into distinct modes. The robot is always in exactly one state. Events trigger transitions. For example, a solar panel cleaning robot in Accra has states: IDLE, MOVING_TO_PANEL, CLEANING, RETURNING, CHARGING. If battery < 20%, transition to CHARGING. If cleaning done, transition to RETURNING. This prevents chaosâthe robot never tries to clean and charge at once.

Implement a state machine with a switch-case in Arduino or Python. Use an enum for states. In the loop, read sensors, then switch on current state. Each state has entry actions, exit actions, and transition conditions. Keep states small. For a maze-solving robot, states: FOLLOW_LINE, TURN_LEFT, TURN_RIGHT, DEAD_END. Transitions based on IR sensor readings. A state machine is easy to debug: print the state name every second.

Behavior trees are more flexible for complex tasks. A behavior tree has nodes: Sequence (do all children in order), Selector (try children until one succeeds), and leaf nodes (actions or conditions). For a robot that sorts recycling, the root is a Selector: try PICK_BOTTLE, if fail try PICK_CAN, if fail try PICK_PAPER. Each pick is a Sequence: APPROACH, GRIP, LIFT, MOVE_TO_BIN. Behavior trees are modularâyou can reuse subtrees. They are popular in ROS (Robot Operating System).

For African makers, start with state machines. They are simpler and use less memory. A typical Arduino Uno has 2KB RAMâenough for 10-20 states. Behavior trees need more overhead but scale better. Use a library like BehaviorTree.CPP if you have a Raspberry Pi. Practical tip: draw your state machine on paper before coding. Use circles for states, arrows for transitions. Test each state individually with a push button. For a farm robot that plants seeds, states: DRIVE, DETECT_HOLE, DROP_SEED, COVER. That's four statesâeasy to implement in a weekend.

4. Subsumption Architecture

Subsumption architecture, invented by Rodney Brooks in the 1980s, builds robot control from the bottom up. Instead of one brain planning everything, you have layers of simple behaviors. Each layer runs independently and can suppress (subsume) lower layers. The lowest layer is a reflex: avoid obstacles. The next layer: wander. The next: seek light. The highest: follow a path. When an obstacle appears, the avoid layer overrides everything else. When no obstacle, the seek layer runs.

Each layer is a finite state machine with sensors and actuators. Layers are added incrementally. Start with a robot that just avoids walls using two bump sensors. That's layer 0. Test it. Then add layer 1: drive forward until bump. Layer 1 subsumes layer 0's forward command when a bump occurs. Then layer 2: follow a line. Layer 2 subsumes layer 1 when line sensors see the line. You never rewrite lower layersâyou just add new ones. This is perfect for African makers because you can build a useful robot in one afternoon with just an Arduino and two motors.

Example: A garbage-collecting robot in a Kigali market. Layer 0: avoid people (ultrasonic sensor, stop if < 30 cm). Layer 1: wander randomly. Layer 2: detect trash (color sensor) and move toward it. Layer 3: pick up trash (servo arm). Each layer is a few lines of code. The robot doesn't need a map or plan. It just reacts. Subsumption is robustâif one sensor fails, lower layers still work.

Implementation: Use a priority arbiter. Each layer outputs motor commands (left speed, right speed). The highest-priority layer that is active wins. In code, check layers from highest to lowest. If layer 3 is active, use its output. Else check layer 2, etc. Use a flag for each layer. For a sumo robot, layers: 0) stay in ring (edge sensors), 1) charge forward, 2) push if opponent detected. This architecture is fast, cheap, and reliable. It's how many commercial robots work today.

5. Hybrid and Deliberative Control

Deliberative control means the robot plans before acting. It builds a map, computes a path, then executes. Think of a robot navigating a warehouse in Johannesburg. It uses SLAM (Simultaneous Localization and Mapping) to build a map with a LiDAR. Then A* or Dijkstra's algorithm finds the shortest path. Then a controller follows that path. Deliberative control is smart but slowâplanning can take seconds. It also needs a good map. If the map is wrong, the robot fails.

Hybrid control combines deliberative planning with reactive execution. A high-level planner sets waypoints. A low-level reactive controller (like PID or subsumption) handles immediate obstacles. For example, a delivery robot in Nairobi: the planner says go to room 5. The reactive layer avoids people and chairs. If a new obstacle blocks the path, the reactive layer stops, and the planner replans. This is how most autonomous cars work. The planner runs at 1 Hz, the reactive layer at 50 Hz.

For African makers, hybrid is practical. Use a Raspberry Pi for planning (Python with ROS) and an Arduino for reactive control (C++). Communicate over serial. The Pi sends target speed and heading. The Arduino runs PID to achieve it. For a farm robot that maps soil moisture, the planner decides which grid cells to visit. The reactive layer keeps the robot on a straight line between cells. If a chicken crosses, the reactive layer stops, then resumes.

Real numbers: A LiDAR (RPLIDAR A1) costs about $100. A Raspberry Pi 4 is $35. An Arduino Uno is $5. You can build a hybrid robot for under $200. Start with a simple deliberative planner: a grid map and BFS. Then add a reactive layer: ultrasonic sensors and a PID controller. Test in a 3x3 meter area. Log data. If planning is too slow, reduce map resolution. If reactive layer oscillates, tune PID. Hybrid control gives you the best of both: intelligence and speed. It's how you go from a toy to a real robot.

6. Lab: Implementing PID for a Mobile Robot

In this lab, you will build a mobile robot that drives straight using PID control on wheel encoders. You need: Arduino Uno, L298N motor driver, two DC gear motors with encoders (e.g., 12V, 200 RPM, 20 pulses per revolution), two wheels, a caster wheel, a 12V battery, and a chassis. Total cost: about $25. Tools: screwdriver, USB cable, computer with Arduino IDE.

Step 1: Wire the encoders to Arduino interrupt pins (pin 2 and 3). Wire the motor driver to PWM pins (5, 6, 9, 10). Step 2: Write code to read encoder counts. Use interrupts to count pulses. Calculate speed as pulses per 100 ms. Step 3: Implement PID for each motor. Desired speed = 100 pulses per 100 ms (about 0.5 m/s). Error = desired - actual. Kp=0.5, Ki=0.01, Kd=0.1 as starting values. Output = Kp*error + Ki*integral + Kd*derivative. Clamp output to 0-255 for PWM. Step 4: Test on a flat floor. Mark a 2-meter line. Run the robot. It should go straight. If it veers, adjust Kp. If it oscillates, increase Kd. If it lags, increase Ki slightly. Step 5: Log data to serial. Use Arduino Serial Plotter to see speed vs time. Tune until both motors maintain the same speed within 5% error.

Troubleshooting: If one motor doesn't move, check wiring. If encoder counts are erratic, add a 0.1 ÂµF capacitor across motor terminals. If PID output saturates, reduce Kp. If robot drifts left, increase left motor Kp or decrease right motor Kp. For African makers, test with a fully charged battery. As battery drains, PID will compensateâthat's the point. Run for 5 minutes. The robot should still go straight. If not, your integral term is too small. Write down final PID values. Use them for future robots. This lab teaches you the core of closed-loop control. Master it, and you can control any motor, heater, or servo.

Practical Reference: Robot Control Architectures for African Agribusiness



Robot control architecture is the decision-making backbone that turns sensor readings into motor commands. For African agribusiness â where a single field robot may need to weed cassava, spray maize, and navigate unmapped terrain on intermittent power â the architecture you choose determines cost, reliability, and whether the machine pays for itself within a season. This practical reference gives you the engineering vocabulary, tuning tables, and a lab you can run with a $150 differential-drive kit.



We cover six lessons: open-loop vs closed-loop control, PID tuning methods, state machines and behavior trees, subsumption architecture, hybrid/deliberative control, and a hands-on PID lab. Each section is written for the operator or agritech founder who needs to specify, buy, or build a field robot â not for a robotics PhD.





Open-Loop vs Closed-Loop Control


Open-loop control sends a command without checking the result. A solar-powered irrigator that opens a valve for 20 minutes regardless of soil moisture is open-loop. It is cheap, needs no sensor, and fails silently when the field is already wet. Closed-loop control measures the output and corrects. A soil-moisture sensor feeding back to the valve controller is closed-loop â it costs more but saves water and protects the crop.


For African agritech, the business rule is simple: use open-loop where the environment is predictable and the cost of error is low (conveyor belts, seed counting), and closed-loop where error compounds (spraying, steering, irrigation). A closed-loop sprayer that reads weed density and adjusts nozzle flow can cut herbicide use by 30â60%, which for a 5-hectare maize farm in Kenya at KES 1,200/litre is a direct margin gain.

The proportional term reacts to current error, the integral term removes steady-state bias, and the derivative term damps overshoot. Tuning is the difference between a robot that follows a crop row smoothly and one that oscillates into the plants.

State Machines and Behavior Trees


A finite state machine (FSM) is a set of states (IDLE, DRIVE, SPRAY, TURN, FAULT) with transitions. It is easy to reason about and cheap to run on a microcontroller. A behavior tree (BT) is a hierarchical tree of tasks with fallback and sequence nodes. BTs scale better when you add behaviors â a weeding robot that must also avoid children, recharge, and return to base quickly becomes unmaintainable as an FSM.


Business rule: use FSM for a single-purpose machine (a seed drill), use BT for multi-purpose field robots that will get new features every season. Both run on a Raspberry Pi Zero 2 W or an ESP32 for the reactive layer.



Subsumption Architecture


Rodney Brooks' subsumption architecture layers simple behaviors, each of which can override lower-priority ones. An obstacle-avoidance behavior subsumes row-following; a cliff-detection behavior subsumes both. There is no central world model â which makes it fast, robust, and cheap. For African conditions â dust, heat, intermittent GPS â subsumption is attractive because it degrades gracefully. If GPS drops, the robot keeps following the row using vision alone.


The trade-off is that subsumption cannot plan a route around a flooded section of field. That is why most modern field robots use hybrid control.



Hybrid and Deliberative Control


Hybrid control combines a fast reactive layer (PID + subsumption) with a slow deliberative layer (path planning, crop maps, task scheduling). The deliberative layer runs on a phone, laptop, or cloud link and updates the reactive layer's setpoints every few seconds. Deliberative-only control â a robot that plans every move â is too slow and too fragile for field work. Reactive-only control cannot optimize a season's spraying schedule.


For a 10-hectare farm, a hybrid architecture is the sweet spot: a $200 companion computer runs the planner, a $15 microcontroller runs the PID loops. This is the architecture behind most commercial agri-robots (NaÃ¯o, FarmWise, Ecorobotix) and is the one we recommend for African agritech startups.




â  SAFETY WARNING â Battery and Motor Control

A PID loop that runs away can command a motor to full power indefinitely. On a lithium battery pack (common in African solar-charged robots), this can cause thermal runaway and fire within minutes. Always implement: (1) a hardware emergency stop that cuts motor power, not just a software stop; (2) integral windup limits; (3) a watchdog timer that zeroes motor output if the control loop misses its deadline; (4) a fuse rated to the motor's stall current. Never test PID tuning with the robot's wheels on the ground and the blade/nozzle engaged.
