1. Image Processing Fundamentals

Start by installing OpenCV on your laptop: `pip install opencv-python`. Then grab a photo of a busy street in Lagos or Nairobi using your phone. Load it with `cv2.imread()`. The first thing you'll notice: images are just NumPy arrays of pixel values. A colour image has three channels (Blue, Green, Red in OpenCV). Convert to grayscale with `cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)` to reduce data by two-thirds. Grayscale is enough for most robot vision tasks like line following or detecting a red tomato.

Next, blur the image to remove noise. Use `cv2.GaussianBlur(gray, (5,5), 0)` â the (5,5) is the kernel size. A bigger kernel means more blur but slower processing. On a Raspberry Pi 4, a 5x5 blur on a 640x480 image takes about 2 milliseconds. That matters if your robot must react in under 100 ms.

Edges are where brightness changes sharply. Run `cv2.Canny(gray, 50, 150)` â the two numbers are low and high thresholds. Try 50/150 for outdoor scenes in bright African sunlight; for dark indoor workshops, drop to 30/100. Canny edges are thin and binary (white on black). You can then find contours with `cv2.findContours()`. Filter contours by area â ignore anything smaller than 500 pixels (noise) and larger than 50,000 (background). This is how you detect a soccer ball on a dusty field.

Finally, learn colour thresholding. Convert to HSV with `cv2.cvtColor(img, cv2.COLOR_BGR2HSV)`. Red is tricky because it wraps around 0 and 180. Use two ranges: `(0,100,100)` to `(10,255,255)` and `(170,100,100)` to `(180,255,255)`. For a maize plant, target green: `(35,50,50)` to `(85,255,255)`. Apply `cv2.inRange()` to get a mask. Combine with morphological operations like `cv2.morphologyEx(mask, cv2.MORPH_OPEN, kernel)` to remove small dots. Practice on 10 images from your surroundings. Save your script as `img_basics.py` and run it on a Raspberry Pi camera later.

2. Feature Detection: SIFT, SURF, ORB

Feature detection finds unique points (corners, blobs) that stay recognisable even when the robot moves or lighting changes. SIFT (Scale-Invariant Feature Transform) is the gold standard but slow: on a 640x480 image, it takes ~200 ms on a Raspberry Pi 4. SURF is faster but patented â avoid it for commercial products. ORB (Oriented FAST and Rotated BRIEF) is free, fast (~20 ms), and works well on African outdoor scenes with high contrast. Use ORB for real-time robotics.

To detect and match features: `orb = cv2.ORB_create(nfeatures=500)`. Then `kp, des = orb.detectAndCompute(gray, None)`. `kp` is a list of keypoints; `des` is a 500x32 binary descriptor array. To match two images (e.g., a robot's current view vs. a stored map), use `bf = cv2.BFMatcher(cv2.NORM_HAMMING, crossCheck=True)` and `matches = bf.match(des1, des2)`. Sort matches by distance: `matches = sorted(matches, key=lambda x: x.distance)`. Keep the best 30% â if you have 100 matches, keep 30. If fewer than 10 good matches, the images are probably not the same place.

Real numbers: For a 640x480 image of a building in Accra, ORB finds ~400 keypoints. Matching against a database of 20 images takes ~50 ms on a laptop CPU. On a Raspberry Pi 4, it's ~300 ms â still okay for a robot that moves slowly (0.5 m/s). For faster performance, downscale to 320x240: ORB drops to ~80 ms.

Practical use: visual place recognition for a delivery robot. Store ORB descriptors of 50 landmarks (a specific tree, a painted wall, a market stall). When the robot sees a new image, match against all 50 and pick the best. If match count > 20, you are at that landmark. This works even if lighting changes from morning to afternoon. Test it in your neighbourhood: take 20 photos of distinct spots, then walk a different path and see if your script identifies them. Adjust `nfeatures` to 1000 for more detail if your CPU allows.

3. Object Recognition with Deep Learning

Deep learning for object recognition means using a pre-trained neural network. You don't need a GPU farm. Start with MobileNet-SSD (Single Shot MultiBox Detector) â it runs at 10-15 FPS on a Raspberry Pi 4 with a Coral USB accelerator, or 2-3 FPS on CPU alone. Download the model files: `MobileNetSSD_deploy.caffemodel` and `MobileNetSSD_deploy.prototxt`. Load with `cv2.dnn.readNetFromCaffe()`. The model recognises 20 classes: person, car, bicycle, motorbike, bus, train, truck, bird, cat, dog, and more. That covers many African street scenes.

To run inference: `blob = cv2.dnn.blobFromImage(frame, 0.007843, (300, 300), 127.5)`. Then `net.setInput(blob)` and `detections = net.forward()`. Each detection has a confidence score. Keep only those above 0.5 (50%). For each, extract the bounding box: `box = detections[0, 0, i, 3:7] * np.array([w, h, w, h])`. Draw a rectangle and label. On a 640x480 webcam feed, you'll see ~5-10 detections per frame in a busy market.

For custom objects â say, a specific type of cocoa pod or a locally made robot â you need to train. Use transfer learning with TensorFlow or PyTorch. Collect 200+ images per class. Label them with LabelImg (free tool). Train a MobileNetV2 model for 20 epochs on a Google Colab free GPU (about 10 minutes). Export to TensorFlow Lite for Raspberry Pi. Expect 85-95% accuracy if your images are varied (different angles, lighting, backgrounds).

Deploy on a robot: use ROS (Robot Operating System) with the `cv_bridge` package. Subscribe to `/camera/image_raw`, run inference, publish `/detections` as a custom message. For a pick-and-place robot, trigger the arm when a target object is detected with confidence > 0.7. Test in your workshop: place 5 different objects on a table, run the detector, and log false positives. Adjust the confidence threshold until you get zero false positives on 100 frames.

4. Stereo Vision and Depth Estimation

Stereo vision uses two cameras side by side to estimate distance â like human eyes. You need two identical USB cameras (e.g., Logitech C270) mounted 10 cm apart. Calibrate them first: print a chessboard (9x6 inner corners), take 20 photos from different angles, and run `cv2.stereoCalibrate()`. This gives you the camera matrix and distortion coefficients. Without calibration, depth errors can be 30% or more.

Next, rectify the images so that corresponding points lie on the same horizontal line. Use `cv2.stereoRectify()` and `cv2.initUndistortRectifyMap()`. Then compute disparity with `cv2.StereoSGBM_create(minDisparity=0, numDisparities=64, blockSize=11)`. Disparity is the pixel shift between left and right images. Depth = (focal_length * baseline) / disparity. For a 10 cm baseline and 600-pixel focal length, a disparity of 30 pixels gives depth = (600 * 0.1) / 30 = 2 meters. That's accurate to about Â±10 cm at 2 m.

Practical limits: Stereo fails on textureless surfaces (plain white walls, dusty roads) because there are no features to match. It also fails in direct sunlight if one camera is overexposed. For African outdoor robots, use a polarising filter on both lenses. At night, add IR illuminators. For a 640x480 stereo pair, SGBM runs at ~15 FPS on a laptop, ~3 FPS on Raspberry Pi 4. Downscale to 320x240 for 10 FPS on Pi.

Use depth for obstacle avoidance. On a robot, take the depth map, divide into a 3x3 grid (left, centre, right). If the centre region has depth < 1.0 m, stop or turn. If left is clear (< 2 m), turn left. This simple rule works for a maize field robot avoiding trees. Test with a cardboard box at 0.5 m, 1 m, 2 m, and 3 m. Log the measured depth. Adjust `numDisparities` to 128 for far objects (up to 10 m) but expect more noise.

5. Visual Odometry and SLAM

Visual odometry (VO) estimates how a robot moves by tracking features between consecutive camera frames. SLAM (Simultaneous Localisation and Mapping) builds a map while tracking position. For a ground robot in an African warehouse, use ORB features plus a motion model. Steps: (1) Detect ORB features in frame 1. (2) Detect in frame 2. (3) Match them with BFMatcher. (4) Estimate the essential matrix with `cv2.findEssentialMat()`. (5) Recover rotation and translation with `cv2.recoverPose()`. This gives you the camera's movement (e.g., moved 0.2 m forward, rotated 5Â° left).

Accumulate these movements to get a trajectory. But errors drift: after 10 meters, you might be off by 0.5 m. That's why SLAM adds loop closure â when you recognise a previously seen place, you correct the drift. Use ORB-SLAM2 or ORB-SLAM3 (open-source, runs on ROS). On a Raspberry Pi 4 with a 640x480 camera, ORB-SLAM2 runs at ~5 FPS â enough for a robot moving at 0.3 m/s. On a laptop, it runs at 30 FPS.

For outdoor African environments, monocular SLAM struggles with scale (you don't know if a tree is 5 m or 50 m away). Use stereo SLAM (ORB-SLAM2 with stereo) or add an IMU (Inertial Measurement Unit). A cheap MPU-6050 IMU (â¹200 or $3) gives accelerometer and gyroscope data. Fuse with a Kalman filter: `x = x + v*dt + 0.5*a*dt^2`. This reduces drift by 50% over 100 m.

Practical test: Build a small wheeled robot with a Raspberry Pi, camera, and IMU. Drive it in a 10 m x 10 m square. Log the estimated path vs. actual (measure with tape). After one loop, the error should be < 1 m. If not, tune the ORB feature count (try 1000) and the RANSAC threshold in `findEssentialMat` (try 1.0). Save the map as a point cloud using `pcl` or `open3d`. This map can then be used for path planning.

6. Lab: Object Detection with OpenCV and ROS

In this lab, you will build a ROS node that detects a red ball using OpenCV and publishes its position. You need: a Raspberry Pi 4 (4GB), a Pi Camera v2, ROS Noetic (Ubuntu 20.04), and a red ball (10 cm diameter). Install `cv_bridge` and `usb_cam` or `raspicam_node`. Start the camera: `rosrun raspicam_node raspicam_node`. Verify with `rosrun image_view image_view image:=/raspicam_node/image`.

Create a package: `catkin_create_pkg ball_detector rospy cv_bridge sensor_msgs`. Write a Python script `ball_detector.py`. Subscribe to `/raspicam_node/image/compressed`. Convert to OpenCV with `cv_bridge.imgmsg_to_cv2()`. Convert to HSV. Threshold red: lower1 = (0, 100, 100), upper1 = (10, 255, 255); lower2 = (170, 100, 100), upper2 = (180, 255, 255). Combine masks. Find contours. For each contour, compute the centroid `M = cv2.moments(c)` and `cx = int(M['m10']/M['m00'])`, `cy = int(M['m01']/M['m00'])`. Filter by area > 500 pixels. Publish the centroid as a `geometry_msgs/Point` on `/ball_position`.

Run the node: `rosrun ball_detector ball_detector.py`. In another terminal, `rostopic echo /ball_position`. Move the ball left and right. The x-coordinate should change. For a 640x480 image, x ranges 0-640. If x < 200, the ball is left; if x > 440, right; else centre. Use this to control a robot: if left, turn left; if right, turn right; if centre, go forward. Write a second node `controller.py` that subscribes to `/ball_position` and publishes `/cmd_vel` (Twist messages).

Test in a 2 m x 2 m area. Place the ball at 1 m, 2 m, 3 m. The detector should work up to 3 m if the ball is well lit. In low light, add an LED ring (5V, 1W) around the camera. Log detection rate: aim for > 15 FPS on the Pi. If slower, downscale the image to 320x240 and adjust thresholds. Document your results: distance vs. detection success. This lab gives you a complete perception-action loop for a robot.

Practical Reference: Computer Vision for Robotics in African Agribusiness



Computer vision is where robotics stops being theoretical and starts paying for itself. For African agribusinesses, the practical question is never "which algorithm is best?" but rather "which pipeline can I deploy on a solar-powered rover in a maize field, or on a conveyor in a Nairobi packhouse, without a cloud connection and without a computer science graduate on staff?" This lesson is a working reference: the numbers, tools, and defaults you need to move from a laptop demo to a fielded system.



Across the continent, the economics are compelling. A single trained human inspector on a tomato grading line costs roughly $150â$300 per month in East Africa and can process about 4â6 tonnes per shift with 85â92% accuracy. A vision-enabled robotic arm running OpenCV and ROS can process the same line at 3â5x throughput with 95%+ accuracy, but only if the camera, lighting, and calibration are specified correctly. Get those wrong and you will spend more on integration than on labour savings. This reference gives you the numbers to specify correctly the first time.

A vision system that misidentifies a tomato as a defect is a business problem; a vision system that misidentifies a human hand as a tomato is a catastrophe.

Deployment Playbook for African Conditions



1. Design for dust and heat. Global-shutter industrial cameras rated IP67 (Basler ace 2, FLIR Blackfly S) survive maize harvest dust; consumer webcams do not. Enclose all electronics in IP54+ cabinets with active cooling if ambient exceeds 35Â°C â Jetson modules throttle at 85Â°C junction temperature, which happens fast in a Ghanaian packhouse without airflow.



2. Design for intermittent power. A 200 W solar panel with 100 Ah LiFePO4 battery will run a Jetson Orin Nano vision station for 8â10 hours of operation. Size the battery for 1.5x your daily runtime to cover cloudy days. Never rely on grid power for a fielded vision system unless you have a UPS with at least 30 minutes runtime.



3. Calibrate for your crop, not for COCO. A YOLOv8 model trained on COCO will detect "apple" but not "mature green tomato ready for export." Budget 2,000â5,000 labelled images per class. Label in Roboflow (free tier supports 10,000 images) and fine-tune from a YOLOv8n checkpoint â this gets you to 0.70+ mAP in under two weeks with one annotator.



4. Keep inference on-device. Cloud inference adds 200â800 ms latency on 4G and fails entirely during outages. For a conveyor running at 1 m/s, 500 ms of latency means the fruit has moved 50 cm past the gripper. Edge inference is not a preference; it is a requirement.



5. Log everything, review weekly. Publish bounding boxes and confidence scores to a ROS 2 topic, then write to CSV. Review weekly for model drift â lighting changes with the season, and a model trained in the dry season will underperform in the rains. Plan a quarterly retraining cycle.



Quick Reference Checklist



  1. Camera specified? Global shutter for moving conveyors, rolling shutter only for static mounts. IP67 if outdoors.

  2. Lighting controlled? Diffused LED bars at 45Â° to the camera axis; avoid direct sun and shadows. Consistent lighting beats a better model every time.

  3. Calibration done? Intrinsics via chessboard (OpenCV calibrateCamera), extrinsics via hand-eye calibration if on a robot arm.

  4. Edge compute sized? Confirm the model runs at target FPS with headroom; thermal-throttle test at 40Â°C ambient.

  5. Power budget verified? Solar + battery sized for 1.5x daily runtime; UPS on any grid connection.

  6. Safety assessed? E-stop within 1 m, light curtain at cell boundary, ISO 10218/TS 15066 risk assessment documented.

  7. Data pipeline live? ROS 2 topic â CSV logger â weekly drift review. Retraining scheduled quarterly.

  8. Business case validated? Throughput gain Ã unit value > (hardware + integration + 12-month support) Ã· 12. If not, do not deploy.
